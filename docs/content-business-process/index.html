01

結論：原文から記事を作る工程ではない

中心にあるのは、役割の違う情報を混ぜずに管理し、公開できる根拠だけで独自コンテンツを組み立てることです。

第三者データは「需要を知るためのシグナル」。公開記事は、公式根拠・運営者の実体験・人間の編集判断を足して、別の成果物として作る。
Production unit

媒体より先に企画を決める

Threads、Instagram、note、Blogを最初から一式生成しない。読者の完了状態と根拠から、作れる型と媒体を個別判定します。

Evidence boundary

シグナル・事実・体験を分離する

MamariのQ&A、公式情報、本人の使用記録、広告案件は別レーンです。一つを別の役割へ読み替えません。

Business model

初期収益はBlogへ集約する

SNSは発見、noteは本人経験がある時の信頼形成、Blogは実用・選択・収益。直接アフィリエイトはBlogだけです。

04

全体設計：4種類の入力を1つの企画へ

同じテーマでも、何を証明できる入力かが異なります。まずレーンを分け、Editorial Briefで初めて統合します。

01

需要シグナル

Mamari Q&A集計、SNS反応、note有料市場の公開メタデータ。困りごと・対象者・場面の候補を見つける。

02

公式根拠

公的機関、メーカー、規約確認済み企業記事。安全・制度・現行仕様・手順の事実を支える。

03

本人の一次体験

運営者自身の使用条件、期間、結果、失敗、改善。レビュー・note・個人ストーリーの唯一の土台。

04

商用オファー

提携先、遷移先、広告条件、開示文、計測ID。編集評価ではなく、CTAの準備状況だけを担う。

役割を保ったまま参照

Editorial Brief

誰が／いつ／何に困る／何を終えたい、作るコンテンツ型、根拠参照、媒体適格性、足りない入力、レビュー状態を保持する正本。

Raw Archive 原本HTML・metadata・hash。変更しない。 childcare-data-aggregator-data
Research DB / Query 解析・集計・source lineage。公開本文を作らない。 SQLite + datassette_gpt_plugin
Editorial / Article Manager brief、根拠、成果物、修正、GO、人間レビュー。 Hermes Content Studio
Publication / Revenue approved manifestだけを表示。CTAと計測を担当。 my-blog / すくリス
05

実務プロセス：収集から公開まで8段階

プログラム、AI、人間の責任範囲を分けています。AIだけで次段階へ進む箇所はありません。

  1. Discover

    テーマを発見し、問題クラスターを作る

    ProgramHuman
    Input / Action

    Mamariの反復シグナル、note市場の公開観測、SNS反応から、対象者・生活段階・場面・困りごとを候補化。

    Gate

    単語の同居だけで企画にしない。「よくある」「売れている」は母集団と根拠なしに断定しない。

    Output

    誰が／いつ／何に困る／何を終えたい、の4要素を持つ問題クラスター。

  2. Policy

    収集前に規約・robots・許可範囲を固定する

    HumanProgram
    Input / Action

    人が利用規約とrobots.txtを確認し、URL、日時、確認者、hash、許可／禁止pathをDBへ記録。

    Gate

    terms=allowed、robots=allowed、enabled=trueが揃わなければ収集しない。

    Output

    監査可能なSource Policyと、許可済みソースだけのURL inventory。

  3. Collect

    決定論的に取得し、原本と構造化データを分ける

    Program
    Input / Action

    URL queue、低速HTTP、claim/checkpoint、再開、重複排除。HTML・sidecar・SHA-256を原本保存し、ローカルParserで解析。

    Gate

    内部API、ログイン、購入済み状態、非表示の有料本文を使わない。403/429で停止。価格やlikesは上書きせず時点観測。

    Output

    取得元へ戻れるRaw Archive、構造化テーブル、parse error、観測履歴。

  4. Validate

    根拠候補を検証し、Research Bundleへまとめる

    ProgramAIHuman
    Input / Action

    企業記事レーンでは最大30件の候補をホストモデルが支持範囲・関連性で判定。広告、逸話、製品固有主張、一般化を拒否。

    Gate

    証拠文をAIが書き換えない。受理済み根拠だけでチェック項目を作り、各項目からURLと原文spanへ追跡できること。

    Output

    childcare.research-bundle 1.0。Mamariの現行planning bundleは原文なし・source ID中心で、新仕様ではEditorial Briefへの移行対象。

  5. Classify

    読者の完了状態でコンテンツ型を一つ選ぶ

    ProgramHuman
    Input / Action

    primary reader outcomeと必須条件を全ルールへ照合し、8種類のうち0件・1件・複数件を判定。

    Gate

    0件はinsufficient、複数件はambiguousで停止。最初のキーワードや旧AIラベルを正解にしない。

    Output

    人が確認したcontent brief、content kind、根拠参照、足りない入力。

  6. Route

    媒体ごとに適格性と生成希望を分ける

    ProgramHuman
    Input / Action

    Threads、Instagram、note、Blogを個別にeligible／blocked／not_applicable判定。

    Gate

    未指定媒体はrequested=false。本人経験がないnote／レビュー、商用準備がないCTAはblocked。

    Output

    媒体別artifact plan、blocked reason、required input、template ID。

  7. Create

    Article Managerで生成・修正し、人がGOを出す

    AIHuman
    Input / Action

    Research Bundleを情報欠落なくimportし、eligibleかつrequestedな成果物だけをテンプレートで生成。修正、画像生成、再適用を行う。

    Gate

    権利、privacy、fact、experience、editorial、commercial、publishを人が確認。Article Manager自身は公開しない。

    Output

    承認済みartifactと、公開に必要な根拠・レビュー状態を持つPublication Manifest。

  8. Publish

    Blogで公開・収益化し、計測を次の企画へ戻す

    ProgramHuman
    Input / Action

    my-blogはapproved manifestだけをbuild。SNS・noteからBlogへ送客し、必要条件の整理後に検証済みofferを提示。

    Gate

    offer、開示、rel="sponsored"、計測ID、最新の商品条件が欠ければBlog buildを拒否。

    Output

    公開記事、SNS配布物、affiliate click／CVR／収益データ、改善用の反応シグナル。

07

実データ事例：質問1件は、そのまま記事にならない

既存ケース資料では、Mamari質問24893911を原点に、ベビーカー選びの確認用成果物まで変換しています。

  1. 01
    原本とDBを照合原本HTML、取得情報、質問IDが同じ1件を指すことを確認。
  2. 02
    質問内の二つの困りごとを分離質問文の言い換え記事ではなく、分析対象を分ける。
  3. 03
    関連候補8件と比較同じ目的かを一組ずつ確認し、目的が一致する5質問をクラスター化。
  4. 04
    件数と回答状況を集計原文を公開せず、企画を選ぶための内部シグナルへ変換。
  5. 05
    公式仕様を追加メーカー公式の対象月齢・重量・仕様を別根拠として接続。
  6. 06
    読者の完了状態を決定「今買う／B型まで待つ／試して決める」を条件で選ぶ設計書にする。
  7. 07
    content kindを選定記事型はselection guide。本人使用がないためfirst-hand reviewにはしない。
  8. 08
    媒体別に生成可否を決定Blog、Instagram、Threadsを作成。本人経験がないnoteは停止。
  9. 09
    確認用成果物を出力Blog本文、5項目のチェックリスト、Instagram 1枚、Threads投稿文。
このケースが証明する範囲 原本から最終成果物へ変わる内容と、各工程の保存データは確認できます。ただし、本番AI実行、Editorial DB登録、人間承認、Article Manager取込、公開、広告案件接続は未実施です。

確認用Instagram成果物。元質問の本文を転載せず、独自の判断項目へ変換しています。

08

収益化：商品へ急がず、必要条件を先に決める

チェックリストから商品リンクへ直結させません。読者が自分の条件を整理した後に、選定ガイドと検証済みofferへ進みます。

STEP 1

発見・共感

Threads／Instagramで具体的な場面と問いに出会う。

STEP 2

実用

Blogのチェックリストや判断ガイドで行動を進める。

STEP 3

条件の確定

必要な機能、不要な条件、利用場面を言語化する。

STEP 4

選択

商品／アプリの選び方、比較、本人レビューへ進む。

STEP 5

収益

条件が合う時だけ、検証済みアフィリエイトCTAを選ぶ。

Commercial gate

CTAを出す条件

  • activeなoffer
  • 媒体上の提携可否
  • 開示文と広告表示
  • rel="sponsored"
  • click event ID
Freshness gate

公開直前の再確認

  • 商品・アプリの現行仕様
  • 価格・提供条件
  • 遷移先と在庫／配布状態
  • facts checked at
  • 記事と体験表現の整合
Measurement

追う数字

  • checklist start／complete
  • related content click
  • affiliate click
  • offer別CVR
  • 収益／1,000 sessions
09

未接続部分と、実運用へ進む順番

今は「材料がない」のではなく、公開契約と商用ゲートがつながっていない状態です。実装順を崩すと、根拠や権利の境界が再び曖昧になります。

  1. 既存Research DBの状態を正常化する

    runningのimport run 8を調査し、Award parse error 4件を解消または既知エラーとして固定。candidate 44件はdraftのまま扱う。

    要対応

  2. 企業一次情報ソースを人が審査する

    6ソースの利用規約・robots・許可pathをレビュー。allowedになったソースだけで小さなEvidence Runを行う。

    0 / 6

  3. Editorial DB・分類器・媒体適格性を実装する

    8 content kinds、分類停止条件、artifact plan、review event、offer、source lineageを正本化。暗黙のDB書込APIを分離する。

    設計のみ

  4. Publication ManifestとBlog build gateを接続する

    raw原文、未承認レビュー、期限切れfact、未整備CTA、人間未確認の一人称表現をbuild時に拒否する。

    未接続

  5. アフィリエイトoffer・開示・計測を実装する

    Blogだけに商用CTAを置き、広告開示、sponsored属性、campaign／offer ID、click／CVRを一続きにする。

    案件なし

  6. 1テーマのパイロットを本番で一周させる

    「生後0〜3か月の短時間外出」など一つに絞り、発見→根拠→生成→人間承認→公開→計測を通してから横展開する。

    未実施
